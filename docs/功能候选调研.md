## 二、steamcmd 本体支持什么（实测，非文档推测）

来源：本机 `D:\SteamSDK\tools\ContentBuilder\builder\steamcmd.exe`，version `1791918946`。

### ❌ 明确不存在（对你很重要）

实测在命令表里搜 `set_` / `build` / `depot` 全表，**没有** `set_app_build_live`，**也没有** `app_build_status`。`+app_build_status` 只能返回本地安装状态，**不能查构建状态**。

### 值得暴露给工具的关键 convar（`+convar value` 或 vdf 里都能用）

- `@DepotBuilderParallelUploadChunks` = 6 / `@DepotBuilderMaxParallelUploadChunks` = 96 —— 上传并发，**弱网调这个比什么都管用**
- `@cbPartnerUploadChunkSize` = 1000000 —— 分块粒度 1MB（印证"1MB chunk 做增量"）
- `@cDepotBuilderFileChunkingThreads` = 8、`@cFileChunkingSupersectionSizeMB` = 1024
- `@LocalContentServer`、`@ForceContentServer`、`@ForceContentServerType`、`@ForceContentServerHTTPS` —— **本地内容服务器就是靠这几个 convar 接上的**
- `@sStartupScript` —— 启动时执行一段脚本，适合让工具注入一整套 convar

## 四、候选功能清单（按 可行性 × 价值 排序）

价值基准：**一个人维护几个 Steam 版本的独立开发者**。

### P0 — 立刻做，keyless，直接消灭真实盲区

#### 1. 「远端 live 状态」面板：我传上去了，但到底生效没有？
- **前提**：只要 `steamcmd`，**匿名登录即可**，不需要 partner key、不需要管理员
- **实现**：`steamcmd +login anonymous +app_info_print <AppID> +quit`，解析 `depots > <DepotID> > manifests > <branch> > {gid,size,download}` 和 `depots > branches > <branch> > {buildid,timeupdated,timebuildupdated}`。与本地 `output\app_build_<AppID>.log` 里的 `BuildID` 对比。
- **实测证据（本机真实数据）**：
  - 本地最新上传：`output\app_build_3036850.log:5` → `Successfully finished AppID 3036850 build (BuildID 25953999)`（2026-10-15 15:40）
  - 远端 public 分支：`app_info_print 3036850` → `buildid 25899209`、`timeupdated 1791866328`（= 2026-10-13 前后）
  - 主游戏 2670430 → `buildid 15834364`、`timeupdated 1727353450`（≈ 2024-09）
  - **结论：最新那次上传没有 set live。** 而 `app_3036850.vdf:26` 的 `SetLive` 是注释掉的，`build.ps1` / `check.ps1` 里 grep 不到任何 `SetLive` 处理（实测 NOT PRESENT）。工具若早就有这块面板，这个坑第一次就能看见。
- **可行性**：✅ 可用（keyless） · **价值：极高**
- ⚠️ 限制：`privatebranches` 为 `1`（3036850 / 2670430 / 2725440 都是），**带密码的私有 beta 分支不会出现在返回里**，面板要如实标"看不到私有分支"。

#### 2. 构建后自动判定"是否需要 set live"并给出明确指引
- **前提**：无额外前提
- **实现**：读回 `branches` 后，若 `buildid != 本地最新 BuildID`，直接提示"这次 build 已上传但未 live；default 分支必须去后台 Builds 页面手动 Set Build Live"。若 vdf 里 `SetLive` 指向某个 beta 分支，则提示"已尝试设为 <branch> live，请在后台确认"。
- **可行性**：✅ 可用 · **价值：极高**（这是"传了没效果"的唯一根因）

#### 3. 一键修复仓库里的漂移（drift）
- **实现**：解析 `app_info_print` 的 depot 列表 ↔ 本地 `scripts\<App>\*.vdf`，报出：
  - depot 在后台存在但本地没有任何脚本 → 传不上去（**当前 demo 3036850 有 depot 3036852 = Linux，本地 `scripts\AbyaDemo\` 只有 3036851/3036853，Linux 从来没传过**）
  - depot 在本地有脚本但后台列表里没有 → 白忙
  - `DepotID` 与 app 脚本里的键不一致（`check.ps1:119` 已做静态版，可升级成"对远端核对"）
- **实测证据**：`app_info_print 3036850` 的 depot 键实测为 `[3036850, 3036851, 3036852, 3036853]`；`2670430 → [2670430,2670431,2670432,2670433]`；`2725440 → [2725440,2725441,2725442]`
- **可行性**：✅ 可用 · **价值：高**

#### 4. 本地 build 状态仪表盘：把 depot 日志解析成结构化增量报告
- **实现**：直接解析现成产物，不需要新工具：
  - `output\depot_build_<DepotID>.log`：`Found N files for mapping`、`Found N new chunks ( M used previously )`、`Uploading K out of K missing chunks`、`Success! New manifestID <id> created and K new chunks uploaded` 或 `Success! Previous manifestID <id> reused, no chunks uploaded`
  - `output\<DepotID>_preview.manifest.txt`：表头 `Total number of files / chunks / bytes`，正文每行 `Size Chunks File SHA Flags Name`
- **实测证据**：`depot_build_3036853.log:1393-1394` → `Uploading 201 out of 201 missing chunks` → `Success! New manifestID 502334034596532109 created and 201 new chunks uploaded`；`depot_build_3036851.log:254` → `Success! Previous manifestID 4954118821117868809 reused, no chunks uploaded`
- **可行性**：✅ 可用 · **价值：高**（"这次到底传了多少"一眼可见）

### P1 — 高价值，工作量中等

#### 5. 「排除规则验证器」：把 manifest 和磁盘对账（含目录条目陷阱）
- **实现**：`ContentRoot` 递归枚举 → 套用 `FileExclusion` → 与 `*_preview.manifest.txt` 逐条比对，把差异标红
- **实测（本机跑通的账）**：win64 磁盘 **521 个文件 + 33 个目录 = 554 条目**；套用 10 条排除规则后 **520**；Steam 的 `file_mapping` 报 `Found 550 files`（`depot_build_3036851.log:3`），manifest 表头也是 **550**，差 4 = 磁盘上不存在的 `logs\*`、`tools\*`（宽匹配把**目录条目**也算进去了）
- **实测到的真实陷阱**：`ABYA_PB_BurstDebugInformation_DoNotShip` 目录里那个 160533 字节的 `lib_burst_generated.txt` **确实被挡住了**，但 **目录条目本身仍以 `Flags 40`、0 字节的形式留在 manifest 里**（`3036851_preview.manifest.txt:12`）。也就是说排除规则挡得住文件、挡不住空目录壳。
- **`DepotPath` 陷阱**：`LocalPath "*"` + `DepotPath "."` 能工作，但 depot 根目录**会多一层同名文件夹**，因为 `*` 匹配到目录后按字面量搬过去。给 `<DepotID>/<DepotID>/*` 会让"下载后实际内容"功能误判。
- **可行性**：✅ 可用（纯本地） · **价值：高**

#### 6. 本地内容服务器（LCS）联调闭环
- **好消息**：SDK 自带 `D:\SteamSDK\tools\ContentServer\`（`mongoose-3.1.exe` + `htdocs\index.html`），`build.ps1` **已经支持 `-Local`**：`:28` `[switch]$Local`、`:30` `[string]$LocalRoot`、`:164` 校验 htdocs 存在、`:166-171` 把 `Local` 键写进临时 vdf
- **蒸汽侧接口已实测存在**：`@LocalContentServer`、`@ForceContentServer`、`@ForceContentServerType`、`@ForceContentServerHTTPS` 都是 steamcmd 里真实存在的 convar
- **⚠️ 开箱即坏的默认配置**：`ContentServer\mongoose.conf:25` 写的是 `document_root D:\ContentServer\htdocs`，而实际位置是 `D:\SteamSDK\tools\ContentServer\htdocs`；`:26` 是 `listening_ports 80`（和 Steam 客户端自身服务撞端口）
- **可行性**：✅ 可用但需修配置与联调 · **价值：中高**（省 Steam 带宽 + 秒级迭代，但要先验证客户端连得上）

#### 7. `app_info_find` 驱动的 App 资产发现
- **实现**：`app_info_find common/type beta` / `common/type demo` / `common/developer Pone Games`，实测 **`common/type beta` 返回 35 条**、`common/type *` 返回 1326 个 App（只显示前 1000）
- **价值**：不用后台就能发现"我是不是还有个 Playtest/Demo AppID 没接进工具"（实测 `2725440 = Dashoot: ABYA's Adventure Playtest`，本地 `scripts\` 下**完全没有对应的 vdf**）
- **可行性**：✅ 可用 · **价值：中高**

#### 8. Unity 构建输出 → Steam 上传 直连
- **事实核对**：`D:\Unity Project\AbyaPB\自动化打包说明.md:53-55` 的 `-steamAppType` 只有 `Demo | Body | PlayerTest`；真实 AppID 硬编码在 `Assets\Scripts\Abya\Runtime\Root\RootControler.cs:1994-1997`（`Demo = 3036850u`、`Body = 2670430u`、`PlayerTest = 2725440u`）
- **注意**：`AbyaBuildCli.cs` **没有 `-steamAppId` 参数**，AppID 只能由枚举推导。工具的"挑 App"只能靠名字映射，不能指望 CLI 传进来。
- **README 里的两个坑**：`README_上传说明.md:124-125` 已指出 `DirectFolder` 不清理旧文件（删掉的文件会被重新传上去，建议 `robocopy /MIR`）；而 `自动化打包说明.md:32` 的示例用的是 `AutoGeneratedSubfolder` —— 面板与命令行两套模式对不上
- **可行性**：✅ 可用（拼接命令与目录） · **价值：高**（去掉手工复制那一步）

### P2 — 真实有用但优先级更低

#### 9. `ContentRoot` 漂移 & 清理提醒
- 固定输出目录 + 不清理 = 幽灵文件照传。工具可以对比"上次 build 的 manifest 文件列表 vs 现在磁盘"，列出**只存在于 depot、磁盘上已删**的文件。
- **可行性**：✅ 可用 · **价值：中高**

#### 10. 上传并发与超时可调（弱网生存）
- 把 `@DepotBuilderParallelUploadChunks`、`@DepotBuilderMaxParallelUploadChunks`、`@DepotBuilderProgressTimeout`、`@nPartnerUploadFinalizeTimeoutSecs` 暴露成 UI
- **可行性**：✅ 可用 · **价值：中**

#### 11. InstallScript 全链路（含签名）
- `InstallScript` 键（`_templates\depot_build_1002.vdf:41`）+ steamcmd 的 **`sign_install_script <appid> <in> <out>`**（实测存在）+ **`app_install_script <AppID>`** 本地验证
- **前提**：不需要 partner key（后端签名走 steamcmd 登录态）；需要一份正确的 installscript vdf
- **可行性**：⚠️ 命令可用，但**具体按键没在官方文档里核到**（正文抓不到）· **价值：中**（单人独立游戏基本用不上，除非要装 DirectX/VC 运行库）

#### 12. DLC / SharedInstall / depot 复用
- 实测在别的 App 里能看到 `depotfromapp`（如 413150 出现 `"depotfromapp" "228980"` = Steamworks Common Redistributables），说明**一个 App 可以直接挂别的 App 的 depot**
- **可行性**：⚠️ 读得出来，但**怎么配得靠后台，我没核到权威键名** · **价值：低-中**

#### 13. 发布后内容实测（下载回来比对）
- `download_depot <appid> <depotid> [<manifestid>] [<dest>]` + `manifest_dump <file> 1` + `verify_chunk_store`
- 可以做到"把玩家实际会下载到的东西拉回来，逐字节比对本地构建"
